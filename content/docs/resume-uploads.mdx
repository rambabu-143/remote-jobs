title: Resume Uploads
description: How resume files are validated, stored, and served securely.
---

## Upload path

The apply form's file input (`<input type="file" name="resume" accept=".pdf,.doc,.docx">`)
submits as part of the same `FormData` the Server Action already reads —
no separate upload endpoint, no client-side fetch to a signed URL. Server
Actions accept `multipart/form-data` natively; `formData.get("resume")`
comes back as a `File`.

`applyToJob` (`src/lib/actions/applications.ts`) validates before touching
disk:

```ts
if (!jobId || !(resume instanceof File) || resume.size === 0) {
  return "A resume file is required.";
}
if (!isAllowedResumeType(resume.type)) {
  return "Resume must be a PDF or Word document.";
}
if (resume.size > MAX_RESUME_BYTES) { // 4MB
  return "Resume must be under 4MB.";
}
```

Allowed MIME types (`src/lib/storage.ts`): `application/pdf`,
`application/msword`, and the modern `.docx` type
(`application/vnd.openxmlformats-officedocument.wordprocessingml.document`).

## Server Action body size limit

Next.js caps Server Action request bodies at **1MB by default** — too
small for most resumes. `next.config.ts` raises it:

```ts
experimental: {
  serverActions: { bodySizeLimit: "5mb" },
},
```

(4MB app-level limit + headroom for multipart boundary/header overhead,
per Next's own sizing guidance.)

## Storage

`saveResumeFile()` in `src/lib/storage.ts` writes to `uploads/resumes/`
(project root, gitignored) under a random UUID filename with the original
extension preserved — never the user-supplied filename, which avoids path
traversal and collisions entirely. Only the generated filename is stored
in `Application.resumeFileName`.

<Callout type="info">
This is local disk storage — fine for one instance, but it won't survive
or be shared across a serverless/multi-instance deployment (e.g. Vercel).
Swap to S3/R2 + presigned uploads before deploying there — see
[Deployment & Scaling](/docs/deployment-scaling).
</Callout>

## Serving files securely

Resumes are **not** under `public/` (which would make them guessable and
world-readable). They're served through
`app/api/files/resumes/[filename]/route.ts`, which:

1. Requires a session at all (`401` if signed out)
2. Looks up the `Application` row by `resumeFileName`
3. Allows the request only if the caller **is the applicant** or **is an
   ADMIN** — otherwise `401`
4. Reads the file and returns it with the right `Content-Type`
   (looked up by extension) and `Content-Disposition: inline`

This was verified directly: a signed-out `fetch()` to a real resume URL
returns `{"error":"Unauthorized"}` with status `401`; the owning applicant
or an admin gets the file back with `Content-Type: application/pdf` (or
the appropriate Word type) and status `200`.
