## Login

Supabase Auth (email + password) handles **authentication**; the app's own
`User` table handles **authorization** (the role). They're joined by id:
`User.id` is the Supabase Auth user's id (`auth.users.id`), not an
auto-generated cuid.

`auth()` in `src/lib/auth.ts` is the one function the rest of the app uses.
It calls `supabase.auth.getUser()`, then looks up the matching `User` row
with Prisma and returns `{ user: { id, email, name, role } }` (or `null`).
It's wrapped in React's `cache()` so the Nav and the page itself share one
Supabase round-trip and one Prisma lookup per request.

### Server Actions talk to Supabase directly

Login and registration pass a plain `<form action={...}>` to a Server Action
(`authenticate` / `registerUser` in `src/lib/actions/auth.ts`):

- `authenticate` calls `supabase.auth.signInWithPassword`, then redirects
  admins to `/admin/jobs` and everyone else to `/dashboard`.
- `registerUser` calls `supabase.auth.signUp`, then inserts the `User` row
  (`role: "USER"`) with the new Supabase user's id. If the Supabase project
  requires email confirmation, no session exists yet, so the action returns
  a "check your email" message instead of redirecting.
- Password reset uses Supabase's own flow (`/forgot-password`, `/reset-password`).

Errors are returned as plain strings to `useActionState` on the client, no
client-side fetch, no JSON error shape to parse.

Supabase clients live in `src/lib/supabase/`: `server.ts` (cookie-bound, for
Server Components and Actions), `client.ts` (browser), and `admin.ts`
(service-role key, server-only, used for Storage).

## Roles

Two roles, `USER` (default on signup) and `ADMIN` (only set by seeding or
directly in the database (`UPDATE "User" SET role = 'ADMIN' ...` after registering normally), there's no self-serve way to become an admin,
by design).

## Every admin surface is checked twice

`/admin/*` and `/docs/*` need an ADMIN. `proxy.ts` only confirms a session
exists; the ADMIN role check is enforced by the route layout and again in
every mutation:

### 1. `src/proxy.ts` (request-level, before rendering)

`proxy.ts` (the Next 16 rename of `middleware.ts`) creates a Supabase server
client, calls `supabase.auth.getUser()` (which also refreshes the session
cookie so Server Components never see an expired one), and redirects
signed-out users to `/login` for `/admin`, `/docs`, `/dashboard` and
`/pricing`.

It only checks **"is there a user?"**, not the role. The role lives in
Prisma, and a database round-trip on every request isn't something proxy
should do, so the ADMIN check happens in the layouts and actions below.

Next.js explicitly documents `proxy.ts` as an *optimistic* check only, it
shouldn't be trusted as the sole authorization mechanism. That's why there's
always a second check.

### 2. The route's own layout (component-level, on every render)

`app/(site)/admin/layout.tsx` and `app/docs/layout.tsx` both independently
call `auth()` and `redirect("/login")` if the session isn't an admin. Two
lines of code, and it means even if `proxy.ts`'s matcher config ever drifts
(a typo, a route added outside `/admin` or `/docs` that should've been
covered, `proxy.ts` skipped entirely in some deployment), the page itself
still refuses to render for a non-admin.

### 3. Every mutation checks again

Server Actions are reachable by a direct `POST`, not just through the UI,
so every action that touches job or application data calls its own
`requireAdmin()` (in `src/lib/actions/jobs.ts`) before doing anything:

```ts
async function requireAdmin() {
  const session = await auth();
  if (session?.user?.role !== "ADMIN") {
    throw new Error("Unauthorized");
  }
  return session;
}
```

`applyToJob` (the one non-admin action that touches sensitive data)
similarly requires a session, a `PUBLISHED` job, and an active subscription
(admins are exempt from the subscription check).

This is the same "check it where the data actually moves, not just where
the button is" principle documented in Next.js's own Server Actions guide.
